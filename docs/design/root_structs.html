Root structs: library state with independent storage

Status: accepted direction, implementation planned. This document describes the target, not an implemented language feature. Establish root structs first; evaluating a stdlib replacement for reusable and reusable[] is a separate milestone and is not a prerequisite for shipping root structs.

Motivation

A library should be able to package its state in one type, initialized by one declaration. Today a struct may contain only one resizable value, on its tail. A library needing two independently growing arrays must ask its user to declare both arrays and assemble a borrowed context. This makes library state awkward to instantiate and expose, even when its complete storage requirements are known statically.

Root structs group independently stored values under one owning lifetime. They do not put several growing arrays into one contiguous byte image, relocate fields on growth, or introduce a heap allocator. Every simultaneously live resizable component still tops its own data stack.

root struct ParserState {
    tokens: Token[>..] = [],
    work: i64[>..<] = [],
    position: i64 = 0
}

var parser = ParserState { .. };
parse(parser, input);

fn parse(state: ParserState&, input: u8[:]) {
    // Ordinary field access and UFCS, with independent array storage.
}

The illustration assumes a separately declared Token type. Root structs are useful for parser state, parallel arrays, lookup structures with separate metadata, and pools. They remain worthwhile if reusable pools stay built in.

Syntax and explicit contract

Use root struct, retaining struct fields, type arguments, defaults, namespaces, and function-based methods. Store the distinction on the existing struct declaration/instantiation rather than creating a separate family of field-access AST nodes.

Treat root as a contextual modifier immediately before struct at a type declaration. Existing variables, fields, parameters, and functions named root remain legal. Do not reserve the word throughout the language merely to parse this modifier.

The modifier means that owning instances are storage roots. It does not mean that the declaration or instance must be at file scope. An explicitly declared root struct retains its restrictions with zero or one resizable field, including in generic specializations. Ordinary structs retain their current placement and layout rules; adding a second resizable field to one remains an error suggesting root struct.

Inference alone would make a field edit, or a generic specialization, change a type's placement, copying, and representation contract. A replacement for struct would obscure how much existing struct behavior remains. local would misdescribe globals, and stack would distinguish little in Goose.

For comparison, Rust infers dynamically sized struct restrictions from an unsized last field, still describing one object; C# explicitly marks its restricted ref struct category. Neither has the same rules as this proposal. References: Rust dynamically sized types, C# ref structs.

V1 ownership and placement

Use V1 rule
Local or global var/let Allowed; construct directly at its declaration using a literal and field defaults.
Fields Ordinary fields and multiple independently stored resizable fields, in any order. Their own existing element, construction, and lifetime restrictions still apply.
Root owner inside another struct Forbidden by value, including inside another root struct.
Root owner as an array/slice element or ADT payload Forbidden, including fixed-length arrays.
Reference to an owner Allowed, including optional references and references stored in fields/arrays when ordinary lifetime rules permit.
Function argument By reference. Untyped parameters bind owning lvalues by reference as for nonfixed values.
Function result References to existing owners may be returned under normal lifetime rules; owning results are deferred. Never return a reference to a local owner.
Unannotated binding from an existing owner Binds by reference, consistent with nonfixed lvalues. Explicit .= remains available.
copy, whole-owner assignment, by-value parameters Forbidden. No implicit descriptor copying or ownership transfer.
Temporary owners Forbidden; owning construction requires a named local/global declaration.
Field assignment and array operations Use the field's usual rules, including shrink and construction checks.
Whole-owner raw serialization or C ABI Unsupported; explicitly supported component operations remain available.
Transfer into a worker Unsupported, including implicit capture of a root global. See the threading rules below.

The prohibition on ownership nesting does not prohibit ordinary fields whose types are existing resizable-tailed structs. Such a field is an independently stored component with its existing internal layout. A root struct itself is never such a by-value component in v1. Variable-size ordinary fields likewise retain their construction rules; the enclosing root has no contiguous image.

struct Context { parser: ParserState& }   // Borrowing is allowed.
struct Object { parser: ParserState }     // Owning containment is an error.

Diagnose the prohibited use with the declaration and field/element/argument path, and suggest a reference or a local/global owner. For example:

ParserState is a root struct and cannot be stored by value in Object.parser.
Declare it as a local/global variable, or store ParserState&.

Enforce the rules through aliases, generic instantiation, inferred types, defaults, inferred results, and unreachable/standalone checking as applicable. An apparently fixed-size control record must never escape the owning rules. const and writability follow existing struct and reference rules, including their existing treatment of reference-valued fields; add no blanket transitive immutability rule.

Storage and construction

An instance has a stable control record for ordinary fields and component metadata. Each resizable component has its own stable element region, length header, and access to its data stack. Use existing representations for ordinary components where possible. The control record is an implementation detail, not a fixed-size Goose value that can be copied or serialized.

The number of component stacks is statically determined by the instantiated type and owning declarations. Lifetime-disjoint owners can reuse stack indices as existing locals do. Globals use dedicated component storage. Restore all owned stack watermarks on scope exit, including break, continue, ordinary returns, and return from. Partial construction must also restore acquired storage without publishing an incomplete owner.

Evaluate field initializers once, in declaration order. Preserve checks against observing under-construction storage. A completed owner can subsequently be initialized further by functions taking its reference. Do not introduce destructors, automatic resource cleanup, runtime owner counts, or moves.

A root owner holding data stacks is subject to the existing recursive-cycle restrictions even though its metadata has constant size. It cannot be live across a recursive-cycle call that would require another set of stacks for each activation. Passing an owner declared outside the cycle by reference remains the intended pattern. Capturing such a reference in a nested function or a compile-time function value follows existing capture and escape rules.

Component identity and lifetime analysis

An enclosing variable's lifetime is not sufficient to identify its storage. Represent independently stored components with identities equivalent to an owning declaration plus a field path:

(state, .tokens)
(state, .work)

These share an enclosing lifetime but are different regions. Preserve this distinction through field projection, direct and optional owner references, branches, rebinding, calls, returned references, globals, captures, and stored references. An unknown reference carries a conservative set of possible regions; never promote a lifetime bound to an exact component identity.

In particular:

  • Growing one field does not interfere with construction in another field.
  • Shrinking one field does not invalidate references into another field, including when their element types are identical.
  • Shrinking a field still rejects any live view or holder that can refer into that field, across calls and reference aliases.
  • index_of must establish the particular array, not merely the owner. Two arrays of the same element type in one root remain distinguishable.
  • Whole-array references name their headers; element references name the element region. A shrink must preserve the existing distinction.
  • Self-relative links remain within their permitted contiguous region. A common enclosing owner does not permit links between separate stacks or from its control record into an array. Use ordinary references for those links.
  • Read-back, holder/store records, effect summaries, construction conflicts, and recursive specialization must propagate component identities consistently.

Current code to audit includes RootAlt/Roots in src/ast.h, RootedAtReceiver/OneArrayOf in src/typecheck_types.h, and SoleResizableIn, growth logs and shrink summaries in src/typecheck_builtins.h. The present root-set join invariant merges entries by owning variable; adding paths requires revisiting join/equality/caching laws, not merely adding a field to the structure. Existing packed structs can still share one region: a field path is not automatically a new region everywhere.

During investigation, small typecheck probes against the available compiler showed that a scalar allocator with separate data and freelist arguments accepts a retained reference across reuse. Grouping those arguments in a struct of references instead made the checker conservatively consider the result capable of pointing into the freelist and reject the next allocation. This is evidence of a current precision limit, not a test of root structs. Include this pattern, and two same-typed owned arrays, in the implementation's acceptance cases.

Code generation and performance

Preserving efficient array access is an explicit requirement. A root reference must not become an unexplained permanent extra load inside hot loops or disable the existing array optimizations merely because arrays are grouped.

The current backend already has relevant machinery:

  • ParamFields in src/codegen_frames.h passes slices, fat references and pool references as separate C parameters. This avoids platform ABI costs and alias-related reloads of aggregate argument copies.
  • Stack tops are cached in C locals, with synchronization around calls and exits (RefTopsOk, HandedStacks, SyncReach, Top/TopW).
  • BCE's hoistrefs and hoistfields let codegen cache array bases and lengths when a loop cannot invalidate or rebind them.
  • Existing frame objects keep fixed prefixes and a resizable tail's header outside the element region.

A stable control-record reference is a reasonable v1 representation, but field projections must expose their normal header/stack information to those passes. Track every stack a root argument or captured root can reach. Flush and reload cached metadata when a call may mutate it, without assuming two parameters are distinct owners. Rebinding, globals, callbacks and nonlocal returns require the same care as existing references. Preserve observable left-to-right sampling.

Inspect generated C as well as timings. Compare direct array arguments, an ordinary one-tail struct, a root with two arrays, a borrowed context, and the existing reusable pool. Cover reads, growth, freelist churn, same-typed fields, out-of-line calls, aliasing parameters, callbacks, and branches selecting owners. Check that base/length reads are hoisted where valid and that unrelated component mutations do not force unnecessary reloads or lose bounds-check elimination. Exercise O0/O2 and TinyCC/native C; include Windows x64 and other CI targets for ABI-sensitive changes. Record reservation count and code size as well as runtime.

Do not promise zero overhead based only on an inlined benchmark. Keep existing reusable until a migration has demonstrated acceptable behavior and performance. For initial root support, report material regressions explicitly and fix basic integration with existing optimizations before calling the feature complete.

Two more ambitious optimizations are deferred:

  1. Known-owner specialization. Where whole-program provenance proves exactly one possible instance, compile access directly to that instance's fields. A unique type is not proof of a unique live instance: repeated declarations, recursion, worker instances, aliases and reentrancy must be considered.
  2. Field-by-field lowering. Treat an owner as component locals and pass the required headers, stack handles and field addresses as separate arguments. This may recover today's pool calling convention. Preserve writes and owner identity; scalar copies of mutable fields are not a substitute for shared locations. Materialize a descriptor when addressability or reference storage requires one. Measure register pressure, argument count and code growth.

Keep the v1 language contract independent of either ABI strategy so that these can be introduced without changing user code.

Serialization, workers, and other boundaries

V1 has no root-level to_bytes, bytes_of, from_bytes, raw equality/copying, or public foreign value layout. A root owner has no single contiguous image, even when every component is individually flat. Do not accidentally accept it through existing flatness or fixed-size predicates.

Serializing or viewing an eligible component, such as pool.items, remains an ordinary operation under the existing image-safety and lifetime rules. Such an image contains the items, not the root's other fields or freelist. Loading it into an existing component obeys ordinary assignment/shrink rules. Libraries that need a coordinated snapshot can define an explicit data format later.

There are existing reusable-to-worker cases: test/threads/thread_globals.goose copies both a reusable slot pool and a reusable slice pool from the spawning instance, preserving freelist state, and tests a worker spawning another worker. Current codegen explicitly copies the freelist beside the data. Preserve that behavior for existing reusable.

Root v1 rejects passing an owning root to thread_spawn or a queue, sending a reference to it, and any worker's direct or transitive use of a root global which would require implicitly copying that owner. Diagnose the reachable global/call path. A root local constructed within a worker needs no transfer and is allowed. An unrelated root global unused by the worker must not reject the program. Existing rules still govern passing eligible components as copied data; never transfer descriptor pointers or infer transferability from flat contents.

Worker snapshot support can follow later by reconstructing independent storage for every component, copying the relevant metadata, and handling only reference forms for which transfer is already legal. This is an explicit compatibility gap to resolve before claiming that stdlib pools replace every reusable use.

Formatting and reflection must distinguish inspecting a reference from copying or serializing its owner. Retain field access and UFCS; support inspection by reference where it does not request a forbidden value operation. Do not add array operator overloading merely to disguise a container's items field.

Separate follow-up: reusable pools in the stdlib

After root structs work as library state, evaluate:

root struct slot_pool<T> {
    items: T[>..] = [],
    free_slots: i64[>..<] = []
}

var pool = slot_pool<i64> { .. };
let r .= pool.alloc_ref(42);
pool.free(pool.items.index_of(r));

This is proposed library usage, not a promise that root support alone makes all operations implementable. Slot pools require fixed-size elements. A slice pool has its items and a separate structure for free spans. Keep the actual current algorithm as the migration baseline: src/runtime/runtime_impl.h uses an augmented B+ tree, not a linear freelist. Preserve first-fit placement, coalescing, tail reuse and overlap-safe relocation before comparing alternatives.

Preserve the existing safety contract: all published elements remain valid typed values, a free merely marks storage reusable, and a stale reference may observe a replacement value. Double frees are logical errors unless a library adds detection. Freeing does not promise decommit, reservation release, or destruction. Slice relocation does not retarget existing views; fragmentation, high-water storage and copying costs remain.

Expose items explicitly for indexing, slicing and ordinary array algorithms. Its length is the high-water length, not a live-slot count. Live-only iteration requires additional metadata or work. Coordinated reset must update both data and metadata and satisfy the data array's normal shrink rules. Goose currently lacks field privacy: internal-field conventions and checked indexing preserve memory safety, but arbitrary user edits may violate pool invariants. Privacy is a separate possible improvement, not a prerequisite for root structs.

The migration needs the following additional work:

Global component paths

Allow pool-relative references and index/bound types to name a statically resolved global component, for example Node&<u32 in nodes.items> and u32 in nodes.items. Resolve a global declaration plus field path, not arbitrary expressions or rebindable references. Preserve width checks, exact-root rules, type identity and the existing no-shrink rule for index-typed arrays. Do not silently interpret in nodes as whichever field looks like the data array.

This extension can follow initial root support; generic root owners do not require a new global-index notation to be useful.

Destination-aware library construction

EmitAlloc currently selects a slot before constructing literals containing relative references there. An ordinary value: T parameter has already received its value elsewhere. Probes confirmed that a self-relative node linking to an existing node typechecks with built-in alloc_ref, but fails through both an ordinary value parameter and a current trailing builder block.

Keep alloc_ref(value) for normally copyable values and investigate a builder API such as pool.alloc_with() { Node { value: 2, next: first } }. Extend the existing construction-destination machinery so a function-value initializer can construct directly into the selected existing slot or append destination. The existing trailing block mechanism alone does not supply this capability.

Preserve self, root checks, evaluation once and in order, construction conflict checking, lexical/nonlocal returns, and publication of a fresh slot only once it contains a valid value. Do not expose uninitialized slots or silently require every slot element to have a default. Use test/storage/alloc_half_built.goose as a compatibility baseline, including initializer side effects on the freelist. This is a general construction feature, not a new pool-specific privilege.

Checked slice position

Current free_slice/realloc_slice can check alignment and complete containment at runtime when provenance cannot prove their input slice belongs to the pool. index_of currently requires stronger static provenance. Expose a general checked slice-to-array position operation (working name range_index): elide checks when proven, reject known foreign storage, otherwise check alignment and the full range. Specify empty-slice behavior explicitly. No library pointer arithmetic or unchecked index fabrication is needed.

Preserve all-build checks for invalid frees, negative/overflowing allocation lengths and element bounds, with validation before metadata changes where the current contract requires it. Slice allocations initialize every added element; relocating slices retain the restriction on self-relative element types. Expose any needed length validation as a general array capability rather than copying runtime constants into the library.

Policy and compatibility

Library variants may add occupancy checks, generations, different span policies, or logical freelist counts over grow-only metadata arrays. Generational handles are an optional API and cannot protect escaped raw references. See slotmap's versioned keys for a useful comparison, not a replacement for Goose's existing reuse semantics.

Retain reusable and reusable[] while measuring and checking the alternative. Only decide on deprecation/removal after construction, relative/index types, reference behavior, worker compatibility, diagnostics and performance have a reviewed migration path. Root structs can ship independently of that decision.

V2 candidates

  • Nested root owners. Permit a root field inside another root, recursively flattening its finite region requirements. Define initialization, projection, lifetime identities and diagnostics before relaxing placement. Ordinary packed structs still cannot silently acquire this layout.
  • Small constant arrays of root owners. Explore slot_pool<T>[N] for a compile-time constant N. The stack requirement is statically multiplied by N; runtime indexing selects an owner descriptor/region set. Define permitted enclosing positions, whole-array references, dynamic-index alias joins, initialization, iteration, N=0, and practical reservation limits. This does not imply resizable or runtime-length arrays of owners. Do not choose an arbitrary small-N language limit before evaluating costs.
  • Known-owner specialization and field-by-field call lowering. As above; preserve addressability and alias semantics while minimizing indirections.
  • Owning factory results. Construct directly into several caller-provided destinations; no descriptor copy masquerading as a move. General copying, reassignment and moving need separate semantics.
  • Worker snapshots and coordinated serialization. Reconstruct independent components with an explicit format/lifecycle contract; never memcpy an owner.

Implementation sequence and acceptance

  1. Frontend foundation. Parse and round-trip the contextual modifier; carry it on struct metadata through generic instantiation and AST cloning. Add syntax coverage and precise errors. During incremental development, reject semantic uses explicitly until their storage support exists: do not allow a root to fall through ordinary fixed/resizable codegen.
  2. Placement, storage classification and provenance. Introduce an explicit owning-layout distinction rather than treating the fixed metadata as a fixed Goose value. Audit size/flatness/copy/containment queries. Implement component identities and their join, specialization and effect-summary behavior.
  3. Ownership and codegen. Allocate and restore all component stacks; support literals/defaults, locals/globals, references, field projection, aliases, captures and calls. Integrate top caches, call reachability and view hoisting. Reject unsupported transfers, copies, nested owners and temporaries before codegen. Update spec, reference, implementation notes and editor support when the feature is usable, without advertising scaffolding as working support.
  4. Library-state acceptance. Demonstrate one-declaration multi-array state used by generic functions, with references retained across unrelated field operations. Test actual runtime behavior and generated code, not just parsing. This milestone does not depend on a reusable replacement.
  5. Pool migration experiment. Port copyable-element slot allocation, compare code and timings, then address the separate construction/path/slice features above and evaluate slice pools and existing worker behavior.

Required focused tests include independent same-typed fields; shrink rejection for the correct component and acceptance for unrelated components; stored, optional, returned and branch-selected owner references; const/writability; generic placement failures; recursion and nonlocal exits; partial initialization; component serialization; forbidden root serialization/FFI/thread use; allowed worker-local owners; and transitive worker-global rejection. Exercise aliases that refer to the same owner as well as distinct owners.

Run the appropriate focused tests during each implementation slice, then the repository's baseline compiler/runtime suite for the complete feature. Extend test/compiler_roots.cpp when changing root-set laws. Keep performance probes repeatable and compare equivalent algorithms; do not conflate a different freelist policy with root-reference overhead.
