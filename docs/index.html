Goose documentation

Goose is a memory-safe systems language with no heap allocator, garbage collector or lifetime annotations (what it is and why). This page is the map of its documentation. The language is described four times, at increasing depth, and the rest of the documents cover the library, the tools and the compiler.

The language, in reading order

Library and tools

  • Standard library: the fifteen modules, std, dictionary, vec, math, os, binary, base64, csv, json, regex, exception, and gfx, audio, physics and ui for graphics, sound, rigid bodies and widgets. All readable Goose under stdlib/.
  • Building programs and using packages: goose build, libraries from git repositories or directories, a program's own C, and how to make a package.
  • Samples: thirty-one complete programs in reading order, from a tour of the language to a JSON parser, a threaded Mandelbrot, a spinning cube and two small games.
  • VS Code extension: highlighting, checks on save, and one-key runs.

Design notes

The reasoning behind features, kept as it was written. The specification and the reference describe what was built; these say why.

  • Index types and checkfree functions: bounds checks moved to where data enters the program, and functions the compiler proves check-free.
  • const for: specialization-time expansion over a struct's fields, a list of types or a list of constants.
  • Relative references: self-relative against pool-relative links, measured.
  • Serialization: the verified loader for structures of relative references.
  • Namespaces: minimal namespaces and qualified names.
  • Builds and packages: the design behind goose build and packages from git.
  • The in-process backend: how TinyCC runs a program inside the compiler, and what it cannot do.
  • String constants, writability and threads: why read-only data cannot be laundered into writable data.
  • Independently owned dynamic data: an editor's open documents as a worked example of slice pools.
  • Standard library design: the library's original scope and conventions.
  • Compiler analyses: an inventory of the checker's analyses and options for simplifying them.
  • Column arrays: a struct-of-arrays storage proposal, not implemented.
  • WebAssembly: running without address-space reservation, fixed partitions against relocating stacks; a proposal.
  • An interpreter for the browser: the compiler built to Wasm with clang, interpreting the C it emits, with pointers as segment handles so stacks can move, and the native packages behind generated thunks; a proposal.
  • A WebAssembly backend from the bytecode: the interpreter's bytecode compiled to a Wasm module on the interpreter's own memory model, with measurements of the ceiling and an estimate of the speedup; a proposal.
